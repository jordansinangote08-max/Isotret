## Recommended execution order

1. **001** first — it's the highest severity (accessibility regression affecting every reduced-motion user on three components at once) and touches only `styles.css`, with no dependency on the others.
2. **002** and **004** next, in either order — both touch `app.js` in the same `renderHome`/`init` neighborhood (lines 342-345 and 859-866) but edit different, non-overlapping lines, so they don't conflict with each other. Apply one, verify, then the other, to keep diffs easy to review individually.
3. **003** anytime — purely a CSS value change in four unrelated selectors, no interaction with any other plan.
4. **005** last — purely additive CSS (new rule + new `@keyframes` + a new reduced-motion block), no dependency on anything else, safe to defer.

## Dependencies between plans

None of the five plans edit the same line of code, so they can technically be applied in any order or independently. The only soft dependency is **002 and 004 both touch `app.js` near each other** — applying them one at a time (rather than both in one sitting) makes it easier to verify each one's feel-check in isolation before the next edit lands on top of it.

## Notes

- All five plans were scoped from a direct audit of this repo (2 source files, no framework, no motion library) — no subagents were used given the codebase size.
- A sixth item was noted during the audit but not turned into a plan: a dead `.btn:hover { transform: translateY(-1px); }` rule at `styles.css:137`, permanently overridden by an unconditional `.btn:hover { transform: none; }` at `styles.css:701` from an earlier "flatter, restrained" design pass. It's stale code, not a behavior bug — worth a driveby cleanup sometime, not worth a full plan.
